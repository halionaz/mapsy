# mapsy — 내 옷장 PRD

> 최종 갱신: 2026-08-01
> 상태: MVP 스펙 확정

---

## 1. 제품 개요

**mapsy**는 패션 관련 서비스를 지향하는 플랫폼이며, 첫 번째 기능으로 **내 옷장**을 구현한다.

내 옷장은 사용자가 보유한 옷을 사진으로 등록하고, 카테고리·색상·사이즈·계절 등으로 분류해 **한눈에 모아보는** 서비스다.

### 핵심 가치
- **등록 마찰 최소화** — 사진 찍고 이름만 붙이면 등록 완료. 나머지는 전부 선택 입력.
- **한눈에 조망** — 내가 어떤 옷을 얼마나 가지고 있는지 그리드로 즉시 파악.
- **정규화된 분류** — 자유 입력을 최소화해 필터가 시간이 지나도 무너지지 않게 한다.

### 핵심 사용 루프
```
촬영/선택 → 타이틀 + 카테고리 입력 → 등록 → 옷장 그리드에 즉시 반영
                    ↑
            (선택) 색상·사이즈·계절·브랜드·가격·핏·메모·태그
```

### v1 (MVP 이후)
- **착용 기록 / 최근 입은순** — ✅ 구현됨 (MAPSY-16). 그날 입은 옷을 옷장 그리드에서 골라 기록하고, 마지막 착용을 카드와 정렬에 반영한다. 상세는 §6.5.
- **빈 옷장 파악** — 카테고리 × 계절 보유 현황판. 0개인 칸을 시각적으로 강조해 "여름 하의가 없네"를 즉시 인지. *(MVP에서 의도적으로 제외. 계절 필드를 MVP에 넣어둔 것이 이 기능의 전제 조건.)*
- 배경 제거(누끼) — 대표 사진을 흰 배경으로 통일해 그리드 완성도 향상
- 통계 — 색상·브랜드·가격 분포, 총 보유 벌수/총액

### v2 이후
- 코디(outfit) 조합 저장 — 이름 붙여 저장하는 기능이 필요해질 때. **`item_wears`가 그 전제**다: 같은 `worn_on`을 가진 행들이 이미 "그날 같이 입은 옷"이라, 조합에 이름을 붙이는 순간 승격시키면 된다
- 착용 달력 / 기간별 통계 — 로그가 이미 전량 내려오므로 화면만 있으면 된다
- 네이티브 앱 (웹뷰 하이브리드)
- 다른 사용자 옷장 탐색 / 공유

### 명시적 비범위 (MVP)
- 완전 오프라인 등록 (IndexedDB 쓰기 큐)
- 다중 사용자 / 소셜 기능

## 3. 사용자 & 계정

- **대상**: 우선 1인(본인) 사용. 다만 데이터 구조와 권한 모델은 다중 사용자를 전제로 설계한다.
- **인증**: Supabase Auth + **Google OAuth 단일 프로바이더**.
  - 회원가입 화면 없음. 로그인 화면은 구글 버튼 하나.
  - 나중에 지인/외부에 열더라도 코드 변경 없음.
- **권한**: 모든 테이블·스토리지에 RLS를 걸어 `user_id = auth.uid()`로 격리한다.
- **세션**: Supabase가 리프레시 토큰을 localStorage에 유지. 기기를 바꿔도 구글 로그인만 하면 데이터가 따라온다.

## 4. 데이터 모델

### 4.1 테이블

```sql
-- 옷 아이템
create table items (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid not null references auth.users(id) on delete cascade,

  -- 필수
  title          text not null,                      -- 옷의 닉네임
  category_id    text not null,                      -- 'top.tshirt_short' 형태 (대분류.소분류)

  -- 선택
  brand          text,
  size           text,                               -- 프리셋 값 또는 자유입력
  fit            text,                               -- 프리셋 값
  colors         text[] not null default '{}',       -- 최대 3개, 첫 번째가 대표색
  seasons        text[] not null default '{}',       -- spring|summer|fall|winter
  price          integer,                            -- KRW, 원 단위
  purchased_at   date,
  purchase_place text,
  memo           text,
  tags           text[] not null default '{}',       -- 자유 태그

  -- 상태
  status         text not null default 'owned',      -- owned | disposed
  is_favorite    boolean not null default false,

  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);

-- 아이템 사진 (아이템당 최대 5장)
create table item_images (
  id           uuid primary key default gen_random_uuid(),
  item_id      uuid not null,
  user_id      uuid not null,
  path         text not null,                        -- 원본 스토리지 경로
  thumb_path   text not null,                        -- 1:1 크롭 썸네일 경로
  sort_order   smallint not null default 0,          -- 0번이 대표 사진, 0~4
  width        integer,
  height       integer,
  created_at   timestamptz not null default now(),

  -- 남의 아이템에 사진을 붙이는 것을 구조적으로 차단
  foreign key (item_id, user_id) references items (id, user_id) on delete cascade,
  -- 순서 변경 중 일시적 중복을 허용하기 위해 커밋 시점 검사
  unique (item_id, sort_order) deferrable initially deferred
);

-- 착용 기록 (§6.5)
create table item_wears (
  id         uuid primary key default gen_random_uuid(),
  item_id    uuid not null,
  user_id    uuid not null,
  worn_on    date not null,                        -- 착용자의 로컬 달력 날짜
  created_at timestamptz not null default now(),

  foreign key (item_id, user_id) references items (id, user_id) on delete cascade,
  -- "그날 입었다"는 사실이지 횟수가 아니다. 토글이 멱등해진다
  unique (item_id, worn_on)
);
```

> **구현체는 [`supabase/migrations/`](../supabase/migrations/)가 단일 진실 공급원**이다. 위 블록은 설계 의도를 읽기 위한 요약이고, CHECK 제약·인덱스·정책 전문은 마이그레이션 파일에 있다. 운영상 알아야 할 것(사진 순서 변경 방법, 팔레트 확장 시 마이그레이션 필요)은 [`supabase/README.md`](../supabase/README.md)에 정리했다.

**설계 노트**
- `colors` / `seasons` / `tags`를 정규화 테이블 대신 **배열 + GIN 인덱스**로 둔다. 이 규모(개인 옷장 수백 벌)에서는 조인 없이 필터가 되고 쿼리가 훨씬 단순하다. 태그 자동완성은 `select distinct unnest(tags)`로 해결.
- 대표 사진은 `cover_image_id` 컬럼 대신 **`sort_order = 0`** 규약으로 정한다. 순환 FK를 피하고, 사진 순서 변경이 곧 대표 변경이 된다.
- **"아이템당 최대 5장"은 `sort_order between 0 and 4` CHECK + `(item_id, sort_order)` UNIQUE 조합으로 강제**한다. 별도 카운트 트리거가 필요 없다.
- `status = 'disposed'`는 삭제가 아니다. 판 옷·버린 옷의 기록은 남기되 기본 조회에서 제외한다.
- **`item_wears`에 `wear_count` 파생 컬럼도, 그것을 유지하는 트리거도 두지 않는다.** 옷장이 이미 전량 로드 + 클라이언트 필터링(§8.4)이라 로그도 통째로 받아 집계한다. 하루 4벌 × 3년 ≈ 4,400행으로, `items` 조회가 이미 받아들이는 규모 안이다. 컬럼 하나를 아끼는 대신 횟수·마지막 착용·그날 같이 입은 옷·나중의 달력이 전부 같은 배열에서 나온다.
- **`worn_on`은 클라이언트가 보내는 로컬 날짜**다. 서버 `now()`로 채우면 UTC라 한국 오전 아홉 시까지가 전날로 기록된다. 컬럼에 기본값을 두지 않은 것이 그 규칙을 강제하는 방법이고, 미래 날짜는 트리거가 막는다(허용 오차 하루 = 시차).
- **색상 팔레트는 DB CHECK로도 고정**한다. 색 추가가 마이그레이션을 요구하게 되는데, 이는 의도된 마찰이다 — 정규화가 깨지면 색상 필터 자체가 성립하지 않는다. 반면 **카테고리는 그룹 접두사만 검증**해서 소분류 추가는 마이그레이션 없이 가능하다.

### 4.2 인덱스

```sql
create index on items (user_id, created_at desc);
create index on items (user_id, category_id);
create index on items using gin (colors);
create index on items using gin (seasons);
create index on items using gin (tags);
create index on item_images (item_id, sort_order);
-- 하루치 조회와 전량 조회. (item_id, worn_on)은 UNIQUE 제약이 이미 인덱싱한다
create index on item_wears (user_id, worn_on desc);
```

### 4.3 RLS

모든 테이블에 동일 패턴 적용:

```sql
alter table items enable row level security;
create policy "items are private to their owner" on items
  for all to authenticated
  using (user_id = (select auth.uid()))
  with check (user_id = (select auth.uid()));
```

`auth.uid()`를 스칼라 서브쿼리로 감싸면 Postgres가 행마다가 아니라 구문당 한 번만 평가한다.

`item_images`와 `item_wears`도 동일. Storage `wardrobe` 버킷(private)에는 경로 첫 세그먼트가 `auth.uid()`와 일치하는지 보는 정책을 SELECT/INSERT/UPDATE/DELETE 각각에 건다. UPDATE에는 `using`과 `with check`를 모두 두어야 남의 폴더로 이름을 바꿔 옮기는 것을 막을 수 있다.

## 5. 프리셋 정의

자유 입력을 허용하면 "베이지 / 아이보리 / 크림 / 오트밀"이 전부 다른 값이 되어 필터가 무너진다. 분류 축은 전부 프리셋으로 정규화하고, 뉘앙스는 타이틀·메모·태그에 적는다.

### 5.1 카테고리 (2단계 고정 프리셋)

| 대분류 | 소분류 |
|---|---|
| **상의** `top` | 반팔티, 긴팔티, 셔츠/블라우스, 니트/스웨터, 후드/맨투맨, 슬리브리스, 기타 상의 |
| **하의** `bottom` | 데님, 슬랙스, 면바지, 트레이닝, 쇼츠, 스커트, 기타 하의 |
| **아우터** `outer` | 자켓, 코트, 패딩, 가디건, 블레이저, 후리스, 베스트, 기타 아우터 |
| **원피스/셋업** `onepiece` | 원피스, 점프수트, 셋업 |
| **신발** `shoes` | 스니커즈, 부츠, 구두, 샌들/슬리퍼, 기타 신발 |
| **가방** `bag` | 백팩, 숄더백, 토트백, 크로스백, 클러치, 기타 가방 |
| **액세서리** `accessory` | 모자, 목도리/머플러, 장갑, 벨트, 주얼리, 시계, 안경/선글라스, 양말, 기타 액세서리 |
| **기타** `etc` | 기타 |

카테고리는 **필수**. 소분류를 고르면 대분류가 자동 결정된다.

### 5.2 태그 (자유, 선택)

프리셋으로 표현되지 않는 축을 담는다. 예: `#테크웨어` `#출근용` `#러닝` `#여행용` `#선물받음`

오타·중복 방지를 위해 **기존 입력값 자동완성**을 제공한다.

### 5.3 색상 팔레트 (16색, 최대 3개 다중 선택)

블랙 · 화이트 · 그레이 · 베이지 · 브라운 · 네이비 · 블루 · 스카이 · 그린 · 카키 · 옐로우 · 오렌지 · 레드 · 핑크 · 퍼플 · 멀티/패턴

첫 번째 선택이 대표색이며 그리드 카드의 색상 도트로 표시된다.

### 5.4 사이즈 (카테고리별 프리셋 + 자유입력)

| 대분류 | 프리셋 |
|---|---|
| 상의 / 아우터 / 원피스 | XS, S, M, L, XL, XXL, FREE, *직접입력* |
| 하의 | 26 ~ 38 (인치), S, M, L, XL, FREE, *직접입력* |
| 신발 | 220 ~ 300 (5mm 단위), *직접입력* |
| 가방 / 액세서리 / 기타 | FREE, *직접입력* |

필터에서는 **현재 선택된 카테고리에 해당하는 사이즈만** 노출한다.

### 5.5 핏 (카테고리별 프리셋)

| 대분류 | 프리셋 |
|---|---|
| 상의 / 아우터 / 원피스 | 슬림, 레귤러, 세미오버, 오버, 크롭 |
| 하의 | 스키니, 슬림, 스트레이트, 테이퍼드, 와이드, 부츠컷, 크롭 |
| 신발 / 가방 / 액세서리 / 기타 | *(필드 숨김)* |

### 5.6 계절 (다중 선택)

봄 · 여름 · 가을 · 겨울. 다중 선택 가능하며, 미입력을 허용한다.

## 6. 화면 정의

### IA
```
/login              로그인
/                   내 옷장 (홈)
/items/new          아이템 등록
/items/:id          아이템 상세
/items/:id/edit     아이템 편집
/settings           설정
```

MVP는 하단 탭바 없이 단일 화면 + 헤더 액션으로 간다. 다만 레이아웃 컴포넌트를 분리해 v2에서 탭(`옷장 / 코디 / 탐색`)을 추가하기 쉽게 둔다.

### 6.1 내 옷장 (홈)

```
┌───────────────────────┐
│ 내 옷장 (41)      ⚙︎  │  ← 헤더: 보유 벌수 + 설정
│ 🔍 검색                │  ← 타이틀·브랜드·메모·태그 통합 검색
│ [전체][상의][하의][아→ │  ← 대분류 칩, 가로 스크롤
│ ⚙ 필터 2 · 검정× 여름× │  ← 적용된 필터 요약 + 개별 해제
├───────────────────────┤
│ ┌────┐ ┌────┐ ┌────┐ │
│ │ 👕 │ │ 👖 │ │ 🧥 │ │  ← 1:1 썸네일, 무한 스크롤
│ └────┘ └────┘ └────┘ │
│  마산    리바이   발마인 │  ← 타이틀 1줄 말줄임
│ ┌────┐ ┌────┐ ┌────┐ │
│ │ 👗 │ │ 👟 │ │ 🧣 │ │
│ └────┘ └────┘ └────┘ │
│   ⊕ 옷 등록   ✓ 기록하기 │  ← 등록은 정중앙, 기록은 우측 (§6.5)
└───────────────────────┘
```

- **필터 바텀시트**: 대분류 칩으로 못 거르는 축(색상·사이즈·계절·핏·브랜드·태그·즐겨찾기·정렬)을 담는다.
- **필터 조합 규칙**: 축끼리는 **AND**, 같은 축 안의 값끼리는 **OR**.
  예) `상의 AND (블랙 OR 네이비) AND 여름`
- **정렬**: 최근 등록순(기본) / **최근 입은순** / 가격 높은순 / 가격 낮은순 / 이름순.
  기본값은 최근 등록순 그대로다 — 기록이 하나도 없는 첫날에 최근 입은순은 의미 없는 순서이고, 데이터가 쌓였다고 기본값이 저절로 바뀌는 것은 설명되지 않는 동작이다.
- **기본 조회 조건**: `status = 'owned'`. 처분한 옷은 설정에서 따로 본다.
- **빈 상태**: 옷이 0벌일 때 등록 유도 화면.

### 6.2 아이템 등록

3단 구성으로, **1단계만 채우면 등록 가능**하다.

1. **사진** (필수 1장 이상) — 카메라 촬영 또는 갤러리 선택, 최대 5장. 드래그로 순서 변경, 0번이 대표.
2. **필수** — 타이틀, 카테고리
3. **선택** (접힌 섹션) — 색상 / 사이즈 / 핏 / 계절 / 브랜드 / 가격 / 구매일 / 구매처 / 태그 / 메모

등록 버튼을 누르면 그리드에 **즉시 카드가 나타나고**, 사진 업로드는 백그라운드로 진행된다.

### 6.3 아이템 상세

- 이미지 캐러셀 (좌우 스와이프, 인디케이터)
- 정보 목록 — 입력된 필드만 표시. `착용` 행은 `3일 전 · 총 12번` (§6.5)
- 액션 — 즐겨찾기 토글, **오늘 입었어요 토글**, 편집, 처분 처리, 삭제(확인 다이얼로그)

### 6.4 설정

계정 정보, 처분한 옷 보기, 로그아웃.

### 6.5 착용 기록 (MAPSY-16)

**전제**: 착용 기록 기능이 죽는 이유는 하나다 — 매일 성실해야 데이터가 쌓이는데, 성실함을 요구하는 기능은 오래 못 간다. 그래서 기록을 별도의 할 일로 만들지 않고, **이미 하는 행동(고민될 때 옷장을 여는 것) 안에 끼워넣는다.** 저녁의 회고가 아니라 아침의 선택이 곧 기록이다.

#### 하단 플로팅의 두 구성

```
평상시            ⊕ 옷 등록(중앙)              ✓ 기록하기(우측)
                                              ← 스크롤하면 라벨이 접힘
                                              ← 기록이 있으면 `어제 3벌`

고르는 중   [ 8.14 (어제) ] [  3벌 기록  ] [ ✕ ]
```

- `옷 등록`은 화면 정중앙에 고정, `기록하기`는 앱 컬럼의 오른쪽 끝. 둘 다 하단이라 화면을 열면 눈에 들어오고, 롱프레스 같은 숨은 제스처가 아니다.
- 둘은 같은 크기다. 서열은 **채움**으로 준다 — 등록은 액센트 필에 글로우, 기록은 중립 서피스. 높이가 다른 필 두 개는 하나가 억지로 끼워 넣어진 것처럼 읽힌다.
- 기록이 있으면 `기록하기` 대신 `어제 3벌`이 되고 접히지 않는다. 사라짐이 아니다 — 하루치 기록에 나중에 한 벌을 더하는 것이 보통이라, 버튼은 남아서 무엇을 담고 있는지 말한다.

#### 선택 모드

카드 탭의 의미와 하단 플로팅, 이 둘만 바뀐다. **검색·대분류 칩·필터 시트·갈래별 섹션은 그대로 산다** — 하의를 고르려면 하의 칩을 눌러야 하기 때문이다.

하단이 `[날짜] [제출] [취소]`로 바뀐다. 상단에는 아무것도 붙이지 않는다 — 날짜와 취소는 옷장을 훑는 중에 손이 가는 것들이고, 화면 맨 위는 긴 옷장에서 유일하게 손이 닿지 않는 자리다.

- **날짜는 탭 두 개가 아니라 버튼 하나**다. 날짜가 둘뿐이라, 지금 것을 보여주고 누르면 다른 쪽으로 바뀌는 컨트롤이 같은 말을 절반 폭으로 한다.
- **`8.14 (어제)`처럼 실제 날짜를 같이 적는다.** `어제`만 있으면 어제부터 켜둔 화면에서 무엇을 가리키는지 확인할 방법이 없다.
- **기본값은 어제.** 기록은 실제로 하루 늦게 이뤄진다 — 그날의 옷은 하루가 끝나야 정해지고, 옷장 앱을 열어 그걸 떠올리는 순간은 다음날 아침이다. 오늘은 한 번 눌러 갈 수 있다.
- 취소가 하단에 있는 이유는 아무것도 고르지 않았을 때 제출이 비활성이라, 모드를 빠져나갈 다른 버튼이 없기 때문이다. 셋 중 유일하게 글리프만 쓰는 것이기도 하다 — 라벨 달린 필 셋은 폰 폭을 넘는다.

- 제출 전에 앱을 나가도 고른 것이 살아있다 (localStorage, `features/wear-log/model/wearDraft.ts`). 앱 재시작을 넘겨 살아남으므로 **읽을 때마다** 두 가지를 본다 — 누구의 초안인지(로그아웃 후 다른 사람 화면에서 열리면 안 된다), 그리고 그 날짜가 아직 오늘/어제인지(자정을 넘긴 탭이 그저께를 "어제"라고 부르면 안 된다).
- **삭제된 옷의 id는 두 저장소에 남을 수 있고, 화면이 마지막 관문이다.** 착용 기록 캐시는 `dropItemWears`가 지우지만 그건 같은 탭의 삭제만 닿고, 초안은 아예 닿지 않는다. 그래서 옷장 화면이 개수·그리드·제출을 전부 "지금 아는 옷"으로 한 번 거른다 — 셋이 같은 출처에서 나오므로 사라진 옷은 애초에 화면에 없었던 것이 되고, 따로 알릴 것이 없다.
- 제출은 그날의 **집합을 다시 쓰는 것**이다. 빠진 옷은 지우고 새 옷만 넣는다. 빈 집합 제출은 "그날 기록 지우기"라는 정당한 편집이다.
- **착용 기록이 로드되기 전에는 선택 모드를 열 수 없다.** 제출이 하루를 통째로 덮어쓰므로, 도착하지 않은 목록에서 씨앗을 얻은 선택은 실제 기록 위에 빈 집합을 쓰게 된다.

#### 빈도를 보여주는 방법

- **정렬 축 `최근 입은순` 하나**. 갈래별 섹션 안에서 정렬되므로 상의 섹션 맨 앞이 "요즘 제일 자주 입는 상의"가 된다.
  - 두 단으로 정렬한다: **입은 기록이 있는 것이 먼저**(마지막 착용 최신순), **기록 없는 것이 뒤**(등록 최신순). 섹션 맨 아래가 "등록한 지 오래됐는데 한 번도 안 입은 옷"이 된다.
  - `오래 안 입은순`은 같은 목록을 뒤집은 것뿐이라 넣지 않는다. `많이 입은순`도 넣지 않는다 — 횟수는 기록이 며칠 비면 사실과 어긋나지만, "마지막으로 입은 게 언제"는 더 작은 주장이라 구멍이 있어도 버틴다.
- **카드**에는 기록이 있을 때만 `3일 전` 같은 캡션이 붙는다. 없으면 아무것도 그리지 않는다 — 기능을 켠 직후에는 그 문구가 모든 카드에 붙어서, 정보가 아니라 배경이 된다.
- **상세**에는 `착용` 행 하나로 `3일 전 · 총 12번`. 여기서는 기록이 없을 때 `아직 기록이 없어요`라고 말한다(다른 필드의 `—`는 "미입력"이라 뜻이 다르다).
- 그리드에 **횟수 숫자는 쓰지 않는다.** 순서는 구멍이 있어도 대체로 맞지만, 숫자는 그 구멍을 사실처럼 말한다.

#### 한 벌만 빠르게 — 상세 화면

`오늘 입었어요` 토글 하나(§6.3). 옷장 그리드를 열어 한 칸만 체크하러 가지 않아도 된다.

여기만 **오늘**을 쓴다. 옷장의 기본값이 어제인 것과 어긋나 보이지만 다른 순간이다 — 옷 하나를 열어놓고 누르는 것은 "지금 이걸 입는다"이고, 하단 버튼은 지나간 하루를 채우는 것이다.

## 7. 사진 파이프라인

### 처리 흐름
```
촬영/선택
  → 클라이언트에서 EXIF 방향 보정
  → 원본:   장변 1280px 리사이즈, WebP q=0.82   (~150KB)
  → 썸네일: 400×400 중앙 정사각 크롭, WebP q=0.8 (~25KB)
  → 두 장 모두 Supabase Storage 업로드
```

**클라이언트에서 썸네일을 직접 만드는 이유**: Supabase Storage의 이미지 변환(transform)은 유료 플랜 기능이다. 무료 플랜에서도 동작하도록 2벌을 올린다.

### 스토리지 구조
```
버킷: wardrobe (private)
경로: {user_id}/{item_id}/{image_id}.webp
      {user_id}/{item_id}/{image_id}_thumb.webp
```

- private 버킷 + RLS. 조회는 서명 URL(TTL 1시간)로 하고 클라이언트에서 캐싱한다.
- 아이템 삭제 시 Storage 객체도 함께 정리한다.

### 용량 추산
아이템당 평균 2장 기준 → `(150KB + 25KB) × 2 ≈ 350KB`.
500벌이면 약 **175MB**. Supabase 무료 플랜 1GB 안에서 충분하다.

```
mapsy/
├── pnpm-workspace.yaml
├── package.json
├── docs/
│   └── PRD.md
└── mapsy-frontend/          # Vite + React SPA (PWA)
    ├── src/
    │   ├── app/             # 라우터, 프로바이더, 레이아웃
    │   ├── pages/           # 화면 하나당 하나 (§6의 IA와 1:1)
    │   ├── entities/
    │   │   ├── item/        # 옷 — 타입·쿼리·카드
    │   │   └── wear/        # 착용 기록 — 로그와 집계 (§6.5)
    │   ├── features/
    │   │   ├── auth/
    │   │   ├── item-form/       # 등록·편집 폼
    │   │   ├── item-photos/     # 사진 서명·뷰어
    │   │   ├── wardrobe-filter/ # 검색·필터·정렬
    │   │   └── wear-log/        # 선택 모드·기록 버튼
    │   └── shared/
    │       ├── api/         # supabase 클라이언트, 스토리지
    │       ├── config/      # 카테고리·색상·사이즈·핏 프리셋
    │       ├── lib/         # 이미지 처리, 초성 검색, 달력 날짜
    │       └── ui/
    └── vite.config.ts
```

`entities`가 `features`와 나뉘어 있는 이유는 쓰기 빈도다. 옷은 한 번 등록하고 거의 안 고치고, 착용 기록은 매일 쓴다 — 둘을 한 캐시에 두면 착용 토글 한 번이 옷장 전체를 다시 받아오고 대표 사진 서명 URL을 전부 새로 발급해 그리드의 모든 썸네일이 다시 로드된다.

추후 `mapsy-native/`, `mapsy-server/`, `packages/shared/`(공용 타입·도메인 상수)를 형제 디렉토리로 추가한다.

`mapsy-frontend/styled-system/`은 Panda CSS가 생성하는 디렉토리이므로 gitignore하고 손대지 않는다. `panda.config.ts` 변경 후에는 `panda codegen`을 다시 돌려야 토큰·레시피가 반영된다.

### 8.2.1 스타일링 규약 — Panda CSS

스타일 작업 시 참고 문서와 이 레포의 규약은 **`.claude/skills/panda-css/`** 스킬에 정리되어 있다. 스냅샷을 복사해두는 대신 [panda-css.com/llms.txt](https://panda-css.com/llms.txt)의 섹션별 URL을 실시간으로 조회하도록 라우팅 테이블을 두어, 문서가 낡지 않게 했다.

핵심 규약 요약:

- **레이아웃은 패턴으로** (`hstack` / `vstack` / `grid` / `container`). 화면마다 flex를 손으로 짜지 않는다. 예외는 앱 셸이나 `<main>`처럼 **높이를 분배하는 것이 목적인 구조 컨테이너** — 패턴의 기본값(가운데 정렬·gap)을 취소하려고 옵션을 넘기게 되는 자리에서는 `css({ display: 'flex', flexDirection: 'column' })`이 의도를 더 정직하게 말한다.
- **변형이 있는 컴포넌트는 레시피로** (`cva` / `defineRecipe`). 칩, 버튼, 아이템 카드가 대상.
- **UI 색은 시맨틱 토큰만** 참조한다 (`bg`, `fg`, `border`, `accent`). 컴포넌트가 원시 색상을 직접 이름 부르면 다크모드에서 깨진다.
- **다크모드는 시맨틱 토큰의 `_dark` 조건으로 한 곳에서** 정의한다. 팔레트는 **다크를 기준으로 설계하고 라이트로 뒤집는다** — 옷 사진을 늘어놓는 화면이라 근검정 배경이 사진을 가장 살린다.
- **글자 크기는 `textStyle` 스케일에서만** 고른다 (`display` / `title` / `heading` / `subheading` / `body` / `label` / `caption` / `eyebrow`). `fontSize` + `fontWeight` + `letterSpacing`을 화면마다 손으로 조합하면 스케일이 아니라 값 목록이 된다.
- **포커스 링은 `layerStyle: 'focusable'`** 하나로 붙인다. 이전에는 같은 4줄이 열일곱 군데에 복사돼 있었다.
- **레시피가 이미 정하는 속성을 `cx`로 덮어쓰지 않는다.** 원자 클래스는 특이도가 같아서, 어느 쪽이 이기는지는 Panda가 스타일시트에 쓴 순서에 달린다. 필요하면 레시피에 variant를 추가한다.
- **`_enabled`를 쓰지 않는다.** `:enabled`로 컴파일되는데 이 의사 클래스는 `<a>`에 매치되지 않아서, 버튼처럼 그린 링크(FAB·편집)의 hover·press가 조용히 사라진다. `'&:hover:not(:disabled)'`로 쓴다.
- **16색 옷 팔레트는 시맨틱 토큰이 아닌 별도 토큰 그룹**(`colors.swatch.*`)에 둔다. 이 색들은 도메인 데이터라 라이트/다크에서 동일해야 한다 — 베이지 옷은 어느 테마에서도 베이지다.
- **스타일 객체는 정적 분석 가능해야 한다.** Panda는 빌드타임 추출기라 변수로 만든 스타일은 조용히 CSS를 생성하지 않는다. 런타임 값이 필요하면 CSS 커스텀 프로퍼티로 넘긴다.
- 모바일 우선. base가 모바일이고 브레이크포인트는 위로 올린다.

| UI 프리미티브 | **Ark UI** (헤드리스) | 다이얼로그·바텀시트·토스트의 포커스 트랩, 스크롤 락, 배경 inert 처리, live region을 직접 짜지 않는다. 스타일은 전부 우리 시맨틱 토큰으로 쓴 Panda 레시피 — shadcn/ui와 같은 "코드를 내가 소유한다" 방식이되, Tailwind가 아니라 Panda 위에서. shadcn/ui 자체는 Tailwind 전용이라 이 레포에 붙지 않는다 |

### 8.3 백엔드

**Supabase** — Postgres + Auth + Storage.

- MVP에서는 클라이언트가 Supabase에 직접 접근하고, 보안은 전적으로 RLS가 담당한다.
- 추후 서버 로직(배경 제거 프록시, 외부 API 연동)이 필요해지면 Edge Function 또는 별도 `mapsy-server/`를 추가한다. Postgres 그대로이므로 자체 서버로의 이전 경로도 열려 있다.

### 8.4 조회 전략 — 클라이언트 사이드 필터링

개인 옷장은 수백 벌 규모다. **전체 아이템을 한 번에 로드해 TanStack Query 캐시에 올려두고, 검색·필터·정렬을 전부 클라이언트에서 처리**한다.

| 이점 | 설명 |
|---|---|
| 즉각적 반응 | 필터 칩을 눌렀을 때 네트워크 왕복 없음 |
| 한글 초성 검색 | 서버에서 어려운 초성 매칭을 클라이언트에서 간단히 구현 |
| 낙관적 업데이트 단순화 | 캐시 하나만 갱신하면 모든 뷰가 일관 |

아이템 500벌 기준 JSON은 압축 후 100KB 미만이다. **1,000벌을 넘어가면** 서버 사이드 필터링(GIN 인덱스 활용) + 커서 페이지네이션으로 전환한다.

### 8.5 오프라인 / 실패 처리

**낙관적 UI + 재시도** 전략:

1. 등록 버튼 → 캐시에 즉시 삽입, 그리드에 카드 표시 (업로드 중 오버레이)
2. 백그라운드로 이미지 업로드 → row insert
3. 실패 시 카드에 재시도 배지 표시, 탭하면 재시도
4. 조회 목록은 서비스 워커로 캐싱해 재진입이 빠르다

완전 오프라인 등록(IndexedDB 쓰기 큐)은 MVP 비범위.

## 11. 열린 이슈

아래는 **명시적 결정 없이 기본값으로 정한 항목**이다. 되돌리기 쉬운 것들이지만 기록해둔다.

| 항목 | 기본값 | 비고 |
|---|---|---|
| 색상 다중 선택 | 최대 3개 | 단일 선택으로 단순화할 여지 있음 |
| 통화 | KRW 고정, 원 단위 정수 | 해외 구매 기록이 필요해지면 통화 컬럼 추가 |
| 패키지 매니저 | pnpm workspace | |
| 아이템 정렬 기본값 | 최근 등록순 | 착용 기록이 쌓여도 바꾸지 않는다 (§6.1) |
| 다크모드 | 시스템 설정 추종 (수동 토글 없음) | |
| 착용 기록의 표본 부족 | 그대로 둔다 | 며칠 비면 순위가 흔들린다. `최근 입은순`은 빈도를 주장하지 않아 거짓말은 안 하지만, "기록이 얇을 때 정렬을 감춘다" 같은 규칙은 넣지 않았다 |
| 어제보다 이전 날짜 | 못 쓴다 | 달력 화면이 필요해지면 그때. 로그는 이미 그것을 담을 모양이다 |
| 기록 기본 날짜 | 어제 | 상세의 `오늘 입었어요`만 오늘을 쓴다 (§6.5). 두 기본값이 다른 것은 의도이지만 검증된 것은 아니다 |
| 처분한 옷이 그날 기록에 있을 때 | 개수에 그대로 센다 | 버튼은 `어제 2벌`인데 그리드엔 한 장일 수 있다. 개수는 **기록**을, 그리드는 **옷장**을 말하는 서로 다른 모집단이다. 보유 중인 것만 세도록 좁히면 그 옷은 보이지도 세어지지도 않으면서 제출 집합에는 계속 실린다 |
| 자정을 넘긴 채 열려 있던 초안 | 조용히 닫힌다 | 잘못된 날짜에 쓰는 것보다 낫다고 봤다. 고르던 것이 안내 없이 사라지는 것은 감수한 비용. 창을 계속 앞에 둔 경우까지 `useLocalDays`의 자정 타이머가 덮으므로, 닫히는 시점은 자정 그 순간이다 |
